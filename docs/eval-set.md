# 评测集构成与逐题说明

配套文档：怎么写题、怎么读指标见 `eval/README.md`。这里记录 `eval/questions.jsonl` 里 40 条题的构成、每条的题型与难度，以及 gold 是怎么在语料里定下来的。

## 构成

40 条，覆盖全部 5 个仓库。

| 维度 | 分布 |
| --- | --- |
| 难度 | easy 9 / medium 18 / hard 13 |
| 题型 | 术语精确匹配 6 / 同义改写 7 / 中英混杂 7 / 代码类 8 / 跨节综合 7 / 干扰项 5 |
| gold 长度 | 共 74 个 chunk，平均 1.85 个/题，最多 3 个 |
| gold 所属仓库 | JavaGuide 25 / happy-llm 17 / self-llm 13 / leetcode-master 11 / CS-Notes 8 |

gold 的仓库分布比题目分布更分散，因为一条题的多个 gold 可以跨仓库（例如 q011 同时引 JavaGuide 和 CS-Notes 的垃圾收集器内容），这是故意留的：跨仓库召回也是要测的能力。

题型不是平均分的。术语精确匹配和同义改写各留了足够样本做对照（稀疏检索在这两类上的表现差异是混合检索权重的直接证据）；干扰项少一点但每条都指向一个真实存在的同题多仓库冲突。

## gold 是怎么定的

流程是「先在语料里捞候选，再逐块读一遍确认它回答了问题」。没有一条是凭印象猜的。

1. 用 `.scratch/build_index.py` 把 `chunks_all.jsonl` 导进 SQLite，正文建索引，方便按子串和标题路径检索。
2. 关键词类（q001-q005、q025、q028、q035）直接用子串搜，例如搜 `泊松` 只命中 `fb72d014bf833a14-0008-d958fd43`，读一遍确认它确实解释了阈值为什么取 8。
3. 同义改写类（q006-q009、q026、q027）反过来做：先确认正文用的是什么词（rehash、TIME_WAIT、掩码自注意力……），再确认那块内容回答了问题。
4. 跨节综合类要求 gold 里的每一块都只答一半，缺了另一块答案就不完整。例如 q018 里「01背包」那块只讲二维和一维的遍历顺序，「完全背包」那块只讲组合数还是排列数，两块才算答全。
5. 干扰项类先确认两个仓库真的有同题内容，再从问题措辞上引向其中一个仓库。例如 q022 的 CS-Notes 剑指 Offer 23 和 leetcode-master 142 是同一道题、同一套快慢指针，但代码语言和讲解不同。
6. 定稿后用 `.scratch/verify_questions.py` 复跑一遍：断言每个 gold chunk_id 在语料里存在，并输出难度/题型/gold 长度分布。

## 已知问题

- **难度标是按设计意图给的，不是实测出来的，而且第一轮实测显示它和实际难度对不上。** 用 `HashingEmbedder`（无模型，纯哈希，不是语义模型）建的临时索引跑了一遍，结果 hard 层 R@5 = 46.2% 反而高于 medium 层的 50.0%…实际是 hard 46.2%、medium 50.0%、easy 55.6%，hard 并没有明显更难。逐条看下来，hard 层的跨节综合题（q018/q019/q021/q022/q023/q033/q034）问题里用的都是正文原词（"01 背包""红黑树""快慢指针""虚拟头结点""is_causal"），字符串匹配就能命中；反而 medium 层的同义改写题（q006/q013/q029/q036/q037）才是真正需要语义理解的一层。**结论：difficulty 字段应当按实测结果重新校准，现在的分层指标暂时只能当"设计意图分组"看，不能当"实际难度分组"用。** 等 bge-m3 索引建好后重跑一次再定。
- **一条题被换掉了。** 最初有一条问「图文模型里图片和文字对不齐怎么对齐」，标注时发现候选 chunk（happy-llm 6.4 偏好对齐）讲的是回答风格的偏好对齐，不是视觉-语言对齐，答不了这个问题，整条删除，换成 q031（SFT loss mask 代码）。
- **q006 和 q009 的 gold 是同一块。** 两条从不同角度问同一节内容（摊还成本 / 为什么优先扩容），属于有意保留的重复，用来观察不同措辞下同一块的召回稳定性。如果只想要互不重叠的指标，可以删掉一条。
- **q035 的三个参数不在同一块里。** `--tensor-parallel-size` 和 `--gpu-memory-utilization`、`--max-model-len` 在 DeepSeek-V4 部署文档的参数说明表里都有，但其他部署文档只给了启动命令、没有解释。这条 gold 只取参数说明表，因为另两块不解释参数含义。
- **没有覆盖的语料内容。** self-llm 有大量 GPU 环境配置、模型下载、Ollama 安装类内容，happy-llm 有 tokenizer 训练、Agent 章节，这些没出题。它们不是不重要，是「检索能召回一条安装命令」这种能力用当前指标衡量不出来，硬出题会拉高 Recall 但不增加信息量。
- **难度标是主观的。** 按「关键词是否原样出现、gold 有几块、是否有仓库级干扰」三条给的分，换个人标会有几条漂移（尤其 easy 和 medium 的边界）。上面第一条已经说明它和实测难度不一致。

## 第一轮实测（不是正式指标）

2026-09 用检索层自带的 `HashingEmbedder`（无模型、纯哈希，512 维）建了一份 18,276 块的索引，跑了一遍评测集，目的是验证标注是否自洽、评测脚本是否能端到端跑通。**这不是项目的检索指标**：正式指标要等 bge-m3 建好索引再跑，哈希 embedder 的稠密通道基本没有语义能力。

```text
总体指标（40 条）
  R@1   R@3   R@5   R@10   MRR@10   Hit@1
   17.5%   37.5%   50.0%   62.5%   0.309     17.5%
  命中项平均名次 : 3.40
  未召回         : 15 条

按题型分层（R@5 / MRR@10）
  术语精确匹配  66.7% / 0.492
  同义改写      71.4% / 0.373
  跨节综合      57.1% / 0.386
  干扰项        40.0% / 0.267
  代码类        37.5% / 0.135
  中英混杂      28.6% / 0.238
```

这轮数据已经能看出三件事，等正式索引建好可以对照：

1. 代码类 MRR@10 只有 0.135，明显低于其他题型 —— 代码块即使被召回，也排在很后面，怀疑是代码块切分或嵌入方式的问题，值得单独查。
2. 中英混杂 R@5 最低（28.6%）。HNSW、IVFFLAT、GGUF、`--tensor-parallel-size` 这类纯英文/符号查询在哈希分词下基本没有信号，正好对应失效清单里 q035（vLLM 参数）top-1 命中了一条 Spring 事务的块。
3. 失败案例清单里的 q016 特别典型：gold 是 704 题「二分法第一种写法」，召回的第一条是同一篇文档的「其他语言版本 > Kotlin」。同一篇文档、相邻小节、主题完全一致，说明是块粒度和排序问题，不是召回通道没工作 —— 这正是清单比总分有用的例子。
