# 评测集怎么写、怎么用

这份文档讲两件事：怎么往 `eval/questions.jsonl` 里加题，以及拿到指标之后怎么用它指导调优。读者是改这个项目的人。

## 为什么要有评测集

改检索就是改一堆互相拉扯的旋钮：切块大小、查询改写、混合检索的权重、要不要加 rerank。这些改动几乎每一个都能让**某几条**问题变好、另几条变差。只靠"我试了几个问题感觉变好了"，最后会发现自己在不知道哪次改动把哪类问题弄坏了。

评测集的作用是把"感觉"换成可对比的数字。它同时服务三件事：

1. 有 baseline。改动前跑一次、改动后跑一次，`--compare` 给出每条指标的差值和方向，改好了还是改坏了是算出来的。
2. 能定位。总分涨 2 个点说明不了什么，**哪些题是 hard 层没召回、哪些题 gold 明明在语料里却排在 8 位之后**才是能动手的信息。失败案例清单直接给这个。
3. 防退化。翻 `--compare` 的 "由召回退化为未召回" 那一栏，如果这次改动让 3 条原本能召回的问题丢了，就得先解释清楚值不值。

## 快速开始

```powershell
# 1. 只验证评测逻辑本身，不需要索引，几秒跑完
python tests\test_eval.py

# 2. 跑真实评测（需要检索层 + 建好的索引）
python eval\run_eval.py --index-dir data\index --top-k 10

# 用 onnx embedder 时要把模型目录传进去（PowerShell 里 JSON 里的引号要写成 \"）
python eval\run_eval.py --cfg '{\"model_dir\": \"G:/kb/models/bge-m3\"}'

# 3. 存结果，留着对比
python eval\run_eval.py --out results\run_baseline.json

# 4. 改了一个旋钮，再跑一次并对比
python eval\run_eval.py --no-sparse --out results\run_dense_only.json
python eval\run_eval.py --compare results\run_baseline.json results\run_dense_only.json
```

常用参数：

| 参数 | 说明 |
| --- | --- |
| `--questions` | 评测集路径，默认 `eval/questions.jsonl` |
| `--index-dir` | 索引目录，默认 `data/index` |
| `--top-k` | 检索条数，默认 10 |
| `--no-dense` / `--no-sparse` | 关掉某一路召回，用来做消融 |
| `--rerank` | 开启重排 |
| `--limit N` | 只跑前 N 条，调试用 |
| `--json` | 结果按 JSON 打到 stdout |
| `--out FILE` | 结果存盘，`--compare` 要用 |
| `--failures N` | 失败案例清单最多显示几条，默认全部 |
| `--compare A.json B.json` | 不跑检索，只对比两次运行 |
| `--corpus` | 语料 JSONL，用来给 gold 补 breadcrumb（默认自动找） |
| `--cfg` | 透传给 `Retriever` 的配置，JSON，如 `'{\"model_dir\": \"G:/kb/models/bge-m3\"}'` |

调 `OnnxEmbedder` 的时候要把模型目录传进去，否则 `Retriever` 会因为找不到 embedder 直接报错：

```powershell
python eval\run_eval.py --cfg '{\"model_dir\": \"G:/kb/models/bge-m3\"}' --out results\run_bge_m3.json
```

这里必须写成 `\"`：Windows PowerShell 5.1 把参数交给原生程序前会吃掉一层引号，直接写 `'{"model_dir": "..."}'` 到 Python 那边会变成 `{model_dir: ...}`，报 JSON 解析失败。

`--compare` 的 Δ 是 `B − A`。指标都是越大越好，只有命中项平均名次（`mean_rank`）是越小越好，所以那一行的方向标记单独做了反向处理（`^` 是变好，`v` 是变差）。

## 加一条题

一行一个 JSON，写进 `eval/questions.jsonl`：

```json
{"qid": "q041", "question": "Redis 的渐进式 rehash 为什么要两个哈希表？",
 "gold": ["58e34df80905e379-0009-efb37ae9"],
 "category": "同义改写", "difficulty": "medium",
 "note": "同义改写：问题问「为什么要两个哈希表」，正文写的是 dict[0] 往 dict[1] 迁移 + 渐进式 rehash"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `qid` | 是 | 全文件唯一，格式 `q001` 起顺排 |
| `question` | 是 | 用户会真的这样问的一句话 |
| `gold` | 是 | 标准答案所在的 chunk_id 列表，不能为空 |
| `category` | 否 | 题型，见下节 |
| `difficulty` | 否 | `easy` / `medium` / `hard` |
| `note` | 否 | 这条考什么，一句话 |

`category` 和 `difficulty` 不写的话，程序会从 `note` 里认 `[easy]` 这种标记和 `类别：xxx`；都没有就归到"未分类 / unknown"层，不会报错。但**显式写上更好**，分层指标才干净。

校验很严：缺字段、`gold` 为空、`gold` 不是字符串列表、`qid` 重复、某行不是合法 JSON —— 全部抛 `EvalDataError` 并指出行号和 qid。设计上就是不许静默跳过：评测集被悄悄丢掉 3 条，指标就假了，而且没人会发现。

## 什么样的题是好题

一句话标准：**这条题的答案真的在某几块里，而且换个说法问也还是它。**

### 题面

- 用真实用户的问法。用户不会说"请检索 HashMap 扩容相关内容"，他会说"为什么扩容要重新算一遍哈希"。后者才是要测的东西。
- 一条题只考一个知识点。把三个问题塞进一句话，失败了你不知道是哪个环节断的。
- 别在问题里报出答案所在的文件名或小节名。"`java-collection-questions-02.md` 里 HashMap 阈值是多少"这种题测的是标题匹配，不是检索。

### 答案

- `gold` 必须是**真的能回答这个问题**的块。块里只是提到了关键词，但没给答案，不算 gold。
- 答案横跨多块时就给多个。比如"树化阈值为什么是 8"，一块讲泊松分布和 64 的关系，另一块给常量定义，两块都算 gold。
- `gold` 不要超过 3 个。给太多等于放宽了判定，Recall 会虚高。
- **标 gold 必须打开语料看**，不能凭印象猜 chunk_id。做法是先用 `text LIKE '%关键词%'` 之类的方式把候选捞出来，再逐块读一遍确认它回答了问题。

### 六类题型

评测集要按这六类铺开，不同类别暴露的是检索层不同部分的毛病：

| 类别 | 长什么样 | 谁应该赢 | 用来发现什么 |
| --- | --- | --- | --- |
| 术语精确匹配 | 问题里的词在正文原样出现，如"树化阈值为什么是 8" | 稠密、稀疏都该召回 | 基线。这一类都召回不到，说明索引或切块坏了，先别看别的 |
| 同义改写 | 问题换个说法，如问"为什么要重新计算哈希"而正文写 rehash | 稠密该赢 | 稀疏检索的弱项。稀疏掉、稠密不掉，说明混合检索的权重还合理 |
| 中英混杂 | 缩写和中文混用，如"HNSW 和 IVFFLAT 分别适合什么场景" | 两路都应该能打 | 分词和大小写归一化的问题 |
| 代码类 | 答案在代码块里，如"快速选择的 Java 实现" | 稠密偏弱 | 代码块的切分和嵌入质量。代码被切断了会全灭 |
| 跨节综合 | 要同一篇文档的两三小节拼起来，如"01 背包和完全背包的遍历顺序" | 都偏难 | 切块粒度问题。块切太碎，答案永远凑不齐 |
| 干扰项 | 多个仓库讲同一主题，如反转链表在三个仓库都有 | 都能召回但容易混 | 区分能力和元数据过滤。这条最能暴露"召回了一堆相似但不对的块" |

### 难度标怎么给

- `easy`：关键词几乎原样，top-1 或 top-3 应该命中。这类题掉出 top-5 就是回归。
- `medium`：需要同义理解，或者 gold 有两块。
- `hard`：跨节综合、强干扰、或者答案在长代码块里。hard 层召回率低是正常的，重点看**它有没有随改动变好**。

分层看指标的意义在于：easy 掉、hard 涨，说明这次改动牺牲了基础召回换长尾，得判断值不值；easy 涨、hard 掉，说明改动只是在过拟合关键词。

## 指标怎么读

- **Recall@k**：top-k 里命中任意一个 gold 的比例。衡量"答案有没有被捞进候选池"。R@10 上不去，后面的 rerank 再强也没用，因为重排只能改顺序，不能把不存在的块变出来。
- **MRR@10**：第一个命中项的名次倒数。衡量"排得够不够前"。R@10 高但 MRR@10 低，说明答案在池子里但排得靠后，这时候该上 rerank 或调融合权重。
- **Hit@1**：top-1 就命中的比例。直接决定用户看到的第一条对不对。

组合起来看的几个典型信号：

| 现象 | 大概率的原因 |
| --- | --- |
| R@10 就低 | 召回通道有问题：切块切断、嵌入模型不适配、稀疏/稠密有一路完全没生效 |
| R@10 高、MRR@10 低 | 排序问题，不是召回问题。rerank、RRF 权重、分数归一化 |
| 同一类题整层全灭 | 系统性缺陷，比如代码类全灭 = 代码块处理有问题 |
| easy 掉、hard 涨 | 改动在拿基础召回换长尾 |
| 只有干扰项那几道掉 | 检索在有相似主题时选错了仓库，需要元数据过滤或更强的区分信号 |

## 用失败案例清单驱动调优

总分只告诉你"变好了/变坏了"，失败案例清单告诉你**下一步改什么**。清单里每条给出：问题原文、gold 的 breadcrumb、实际返回的 top-3 breadcrumb。每一项后面都跟着 `[chunk_id]`——同一小节的多个 chunk breadcrumb 完全相同，只列 breadcrumb 没法判断 gold 和 top-1 是不是同一块。

调优时按这个顺序读：

1. **gold 的 breadcrumb 是不是你预期的那一节？** 不是的话，是标注错了或者你对语料的理解不对，先修评测集。
2. **实际 top-3 和 gold 是不是在同一个文档、只是差几节？** 这是排序或粒度问题，相邻块合并、加大 top-k 候选、上 rerank 都值得试。
3. **实际 top-3 全在别的仓库？** 跨仓库干扰，考虑元数据过滤或仓库加权。
4. **实际 top-3 语义上完全不相干？** 召回通道本身没工作，先查嵌入和稀疏索引有没有真的建上。
5. **top-3 里有正确答案的近义块但没标成 gold？** 那可能不是失败，是 gold 标窄了。这种情况要承认并补 gold，而不是留着当成"失败"自我安慰或者自我打击。

改完一定要重新跑一次并 `--compare`。一次只改一个旋钮，不然数字变化归因不了。

## 现在这份评测集的情况

40 条，六类均衡，覆盖全部 5 个仓库。具体分布和每条的设计意图写在 `docs/eval-set.md`。

已知的局限，别拿它当万能的：

- 40 条样本量偏小，单条题的得失就能让 Recall 动 2-3 个百分点。看趋势，别看小数点后第二位。
- gold 是人工标的，块边界附近有主观判断空间（答案的另一半在相邻块里算不算 gold）。
- 这里只测检索有没有把证据捞出来。答案侧另有一套，见下一节；那套测的是「答得有依据吗」，
  不是「答得和标准答案一致吗」。
- 语料是五个特定开源仓库，题目覆盖的主题跟着这几个仓库走，通用性有限。

## 答案侧评测

检索指标全绿也可能答错：gold 捞到了、模型却编了一段。这一层单独测答案，入口是
`eval/run_answer_eval.py`，和检索评测共用 `eval/questions.jsonl`。

```powershell
# 全量，带逐句忠实度判定（每题一次生成 + 一次判定）
python eval\run_answer_eval.py --out results\run_answer_final.json

# 只看拒答和引用，不花判定的 token
python eval\run_answer_eval.py --no-judge --limit 10

# 先小样本试水
python eval\run_answer_eval.py --limit 3
```

输出分三块：拒答、漏斗、引用/忠实度。指标口径如下。

| 指标 | 口径 | 怎么看 |
| --- | --- | --- |
| 拒答率 | `refused` 的题 / 全部 | 高说明提示词或检索有问题 |
| 假拒答 | gold **进了提示词**却拒答 / gold 进了提示词的题数 | 召回到了不敢答，是模型层判得太严，不是检索问题 |
| 漏斗：检索前 k 条 | gold 进了送进提示词的检索结果 | 和检索评测的 Recall@k 应当接近，可交叉验证 |
| 漏斗：被答案引用 | gold 出现在 citations 里 | 与上一行的差额 = 召回了没被引用 |
| 无引用句占比 | 已答的题里没有 `[n]` 的句子比例 | 越高越难核对 |
| 无效引用号 | 正文引用了不存在的编号 | 必须为 0 |
| 平均支持率 | 逐句判定里「能由参考段落支持」的比例 | 剩下的是无依据句，报告会列出原句和原因 |
| 判定失败 | `judge_error` 题数 | 不算进支持率，见下 |

**判定失败为什么不猜。** 判定提示词要求模型回报 `checked`（它数了几句），和实际句数不一致就记
`judge_error`、该题不进支持率分母。模型漏判/多判时给出的比例没有意义，静默算成 100% 是最坏的结果。

**「资料未覆盖：X」不算无依据。** 拒答复核之后模型会写这一行声明缺口，它本来就该没有引用，
既不进「无引用句」统计，也不送判定。

成本：每题生成一次 + 判定一次，40 题约 10 万 token、100 秒左右。`--no-judge` 省掉一半。

当前结果（40 题，2026-11-15，`results/run_answer_final.json`）：

| 指标 | 不复核 | 复核后（现行） |
| --- | --- | --- |
| 拒答 | 4/40 (10.0%) | 1/40 (2.5%) |
| 假拒答 | 0/34 | 0/34 |
| 检索前 5 条含 gold | 34/40 (85.0%) | 34/40 (85.0%) |
| 被答案引用 | 30/40 (75.0%) | 31/40 (77.5%) |
| 无引用句占比 | 8.9% | 5.2% |
| 平均支持率 | 96.9% | 96.1% |
| 无依据句 | 5 | 4 |
| 无效引用号 | 0 | 0 |

局限：

- 判定和生成用同一个模型（deepseek-chat），存在自评偏差。要更硬的结论得换模型交叉判、或人工标 50 条校准。
- 只看「有没有依据」，不看「对不对」。答案和标准答案是否一致，现在还测不了——评测集里没有参考答案字段。
- 支持率按句算，一句话里半对半错会被算成整句不支持。
